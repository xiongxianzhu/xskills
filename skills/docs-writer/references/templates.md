# 文档结构规范

按文档职责选择下列结构。表中的章节是组织建议，不是固定目录；保留读者完成任务所需的内容，不适用的章节直接省略。局部修改沿用现有结构。通用流程见 [SKILL.md](../SKILL.md)。

## README

**文件**：`README.md`。作为项目入口，让读者快速判断用途并完成第一次使用。

**事实来源**：项目入口、包配置、命令脚本、配置示例、许可证、现有文档。

| 建议顺序 | 内容要求 |
| --- | --- |
| 项目简介 | 一至三句说明解决的问题、适用对象和主要边界 |
| 核心能力 | 仅列影响使用判断的已实现能力；与简介重复时省略 |
| 快速开始 | 必要环境、安装、最小配置、启动或首次调用，以及成功判据 |
| 常用操作 | 按需列开发、测试、构建或典型用法，不展开完整运维手册 |
| 文档导航 | 链接已有的部署、架构、技术栈、任务或数据库文档 |
| 其他信息 | 确有需要时补充限制、贡献入口或许可证 |

**写作要求**：

- 快速开始只给一条可靠的主路径；替代安装方式和高级配置链接到专门文档。
- 版本以项目为准，不把本机版本写成最低要求，不编造可发布的包名或安装命令。
- 无运行入口的资料仓库说明如何安装、获取或使用内容，不套用“启动服务”。
- 目录树仅解释重要入口，配一句职责说明，不递归罗列整个仓库。
- 不强制添加架构图、FAQ、路线图、截图或总结。头部样式按 [README 头部与徽章](style-guide.md#readme-头部与徽章) 的适用范围处理。

**验收**：读者能判断是否适用，按说明开始使用，并找到进一步说明；正文没有复制其他文档的细节。

## 部署文档

**文件**：`deployment.md`。让执行者在指定环境完成部署，并能判断结果、处理失败。

**事实来源**：部署脚本、容器或服务配置、CI/CD 工作流、环境变量定义、迁移文件、健康检查实现。区分仓库部署方案和已核实的运行环境。

| 建议顺序 | 内容要求 |
| --- | --- |
| 适用范围 | 环境、部署方式、服务组成及必要版本限制 |
| 前置条件 | 运行时、外部依赖、权限、网络和持久化目录等实际前提 |
| 配置 | 配置来源、必填项、默认值、示例和生效方式；敏感值使用安全的替换项 |
| 首次部署 | 按依赖顺序说明获取制品、安装或构建、初始化、迁移、启动 |
| 验证 | 检查命令或路径、预期状态和最小业务验证；区分进程存活与业务可用 |
| 更新与回滚 | 备份、版本切换、迁移兼容性、回滚条件和可恢复范围 |
| 运维与排障 | 与当前方案相关的日志、状态检查，以及常见故障的定位与处理 |

**写作要求**：

- 明确命令的执行位置、账号权限、先后关系和适用环境，不能混用本地、容器内与宿主机命令。
- 配置较多时用“名称｜用途｜必填/默认值｜示例或来源”表，只列该部署路径需要的项。
- 域名、端口、路径、服务名从配置提取；示例值标明为示例，并集中说明替换方式。不要泄露生产凭据。
- 首次初始化与日常更新分开；有数据变更时说明备份和兼容要求，无数据库时不补迁移章节。
- 回滚区分应用制品、配置和数据。没有可逆迁移或恢复验证时明确恢复限制，不承诺一条命令还原。
- 排障写“现象 → 检查位置 → 处理动作”；不把 `sudo`、关闭鉴权或清空数据作为默认解决方法。
- 可静态核对步骤，不因编写文档执行生产操作。未经运行的结果写为预期，不写“部署成功”。

**验收**：执行前知道条件和影响，执行后有明确检查方法，失败时知道下一步与恢复边界。

## 架构文档

**文件**：`architecture.md`。说明系统边界、组件协作和关键设计约束。

**事实来源**：应用入口、模块调用、路由或消息处理、数据访问、部署拓扑、设计记录。

| 建议顺序 | 内容要求 |
| --- | --- |
| 系统概览 | 系统职责、使用方、外部依赖与范围边界 |
| 组件与职责 | 核心模块或服务的职责、接口和依赖方向 |
| 关键链路 | 代表性的请求、事件或数据流，关键状态变化与失败路径 |
| 设计约束与取舍 | 有依据的边界、设计理由、代价和限制 |
| 横切机制 | 按实际实现说明认证授权、事务、一致性、缓存、异步处理或可观测性 |
| 扩展与演进 | 仅在请求涉及或确有记录时说明扩展点、已知问题与拟议方案 |

**写作要求**：

- 围绕职责和协作解释系统，不把目录树或技术名词清单当作架构。
- 简单关系用文字或表格；多组件协作按需用 Mermaid 架构图或时序图，标明调用、消息或数据的方向。
- 图中节点对应真实模块或明确标记的规划组件，正文与图使用相同名称。
- 区分进程、模块、服务和外部系统，不把普通模块称为微服务，不凭框架推断分层架构。
- 说明现有机制能保证什么、不能保证什么，不把“可扩展、高可用、高性能”当作无证据结论。
- 设计理由来自注释、决策记录或用户说明；没有理由记录时描述行为和限制，不补写作者动机。
- 引用关键源码路径或设计记录即可，不逐行复述代码。部署命令、精确版本和字段定义链接到对应文档。

**验收**：读者能定位职责、追踪一条关键链路并理解边界；现状与规划不会混淆。

## 技术栈文档

**文件**：`tech-stack.md`。记录核心技术、用途、版本依据与维护约束。

**事实来源**：依赖清单、锁文件、运行时声明、构建配置、容器镜像、CI 配置、实际代码使用情况。

**推荐主体**：按后端、前端、数据存储、基础设施、开发与质量工具等实际层次分组，使用“层次｜技术｜版本或约束｜项目用途｜依据”表。只有一个层次时不分组。

**写作要求**：

- 只列影响开发、运行、部署或维护的核心技术，不复制全部直接依赖和传递依赖。
- 版本标明语义：声明范围、锁定版本、镜像标签或已核实的运行版本；无法确认精确版本时保留约束或注明未锁定。
- 例如清单声明 `^3.2.0`、锁文件解析为 `3.2.5`，分别写“声明：`^3.2.0`；锁定：`3.2.5`”，不能推出线上版本。
- 项目用途写具体职责，不抄产品介绍。依赖已声明但未发现使用时，不能写成已启用能力。
- 根据配置区分生产依赖、开发工具和可选组件；存在替代方案时说明实际启用条件。
- 选型理由只记录有依据的决策。用户要求推荐时单列建议并说明约束，不与已用技术混写。
- 仅在影响使用时补充兼容要求、安装入口、升级限制，不重复部署步骤或展开完整架构。

**验收**：每项技术都有实际用途和来源，版本语义准确，读者能判断需要安装和维护什么。

## 开发任务清单

**文件**：`tasks.md`。把已明确的目标拆成可执行、可验收的工作项。

**事实来源**：用户需求、已有任务与问题记录、设计文档、源码及相关验证结果。新需求可形成待办，但不能据此推断已完成。

| 建议顺序 | 内容要求 |
| --- | --- |
| 目标与范围 | 简述本批任务要交付的结果，不重写完整需求文档 |
| 任务列表 | 按里程碑、模块或依赖顺序组织，保持同一维度 |
| 阻塞与待决事项 | 仅列影响实施的实际缺口和所依赖的决定 |

**单项任务**：稳定标识、动作与对象、交付物或修改范围、验收标准、状态；有依赖时写依赖标识。可以用勾选列表或表格，不同时维护两份相同清单。

以下仅演示任务粒度，编号、命令和目标必须按真实项目替换：

```markdown
- [ ] T-03 实现任务列表分页
  - 交付：列表接口支持页码和每页数量，补充调用示例。
  - 依赖：T-02 查询接口。
  - 验收：按已确认的排序返回记录；空页返回空列表；非法参数返回约定错误。
```

**写作要求**：

- 一项任务对应一个可独立验收的结果；大任务按交付物拆分，不按“研究、编码、优化”堆砌空泛阶段。
- 验收写可观察的行为或检查方法，避免“运行正常、性能良好、完成优化”等无法判断的表述。
- 简单任务用 `[ ]` / `[x]`；需区分进行中、阻塞时明确写状态。阻塞项说明原因，不伪装成进行中。
- 仅在交付物存在且验收有依据时标记完成；代码已写但未验证时如实说明。测试通过不等于上线完成。
- 更新清单时保留稳定标识和历史完成状态；仅在发现相反证据时更正并说明原因，不重编号或重置全部任务。
- 优先级、负责人、估时、截止日期只在有需求或依据时添加；推导的顺序注明依赖理由，不编造团队安排。
- 不为显得完整而新增未要求的功能、设计方案或基础设施任务。

**验收**：每项任务都有明确交付物和完成标准，依赖可追踪，状态可信。

## 数据库设计文档

**文件**：`database.md`。说明数据模型、字段语义、完整性约束与演进方式。

**事实来源**：建表 DDL、迁移、ORM 模型、查询及事务代码；仅在已授权且需要时读取数据库元数据。声明描述的是模型、迁移目标还是已核实的数据库实例。

| 建议顺序 | 内容要求 |
| --- | --- |
| 范围与约定 | 数据库类型、版本依据、命名，以及时间、字符集、金额等适用约定 |
| 实体与关系 | 实体职责、关联字段、基数和可选性；关系复杂时使用 ER 图 |
| 表与字段 | 每表用途；字段名、数据库类型及长度/精度、可空性、默认值、业务含义 |
| 键、约束与索引 | 主键、外键、唯一和检查约束；索引列顺序、类型或条件及有依据的用途 |
| 数据规则 | 枚举值、状态含义、删除策略、事务或一致性边界，仅写实际适用规则 |
| 迁移与维护 | 迁移入口、兼容要求、数据修复或回滚限制；详细操作链接部署文档 |

**写作要求**：

- 覆盖约定范围内的表和字段；大型系统按模块拆分，不能静默遗漏字段或只展示少量示例。
- 使用真实数据库类型，不把语言类型直接当列类型；区分应用默认值与数据库默认值，以及空值、空字符串和零。
- 显式区分逻辑关联和物理外键。没有外键约束就写明逻辑关联，不根据命名推断级联行为。
- 组合唯一约束和联合索引写出完整列及顺序，不能把普通索引描述为唯一性保障。
- 记录有依据的枚举、时区、金额精度、敏感字段处理和数据保留规则；无依据时不默认添加软删除、审计字段或加密能力。
- 模型、迁移与实际库结构冲突时说明差异和适用范围，不把未执行迁移当作线上现状。
- 索引建议、规范化建议或新表设计单列为方案，不修改模型或生成迁移来“配合”文档。
- SQL 示例注明方言和适用条件，不执行建表、改表、删表或数据修复来验证文档。

**验收**：读者能理解字段含义、关联和约束，区分实现与建议，并找到演进依据。

## 其他技术文档

保留已有写作能力，按请求使用最小结构：

| 类型 | 建议结构 | 关键检查 |
| --- | --- | --- |
| API 使用说明 | 用途 → 前提 → 参数 → 调用示例 → 返回与错误 | 与当前签名一致，参数与错误有依据；严格接口契约使用 api-docs |
| 教程 | 目标成果 → 前置条件 → 顺序步骤 → 结果验证 | 每步有动作和检查点，不要求每步都附代码或输出 |
| 变更日志 | 版本或日期 → 相关变更分组 → 升级动作 | 区分已发布与未发布，突出破坏性变化；不编造版本、日期或 Issue |

变更分组沿用项目约定，可按新增、变更、弃用、移除、修复、安全分类，仅保留有内容的组。无关的长篇背景、延伸阅读和结尾总结不自动添加。
