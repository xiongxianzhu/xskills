# 写作与校对规范

目标是让读者快速找到事实、完成操作、理解约束。简洁不等于遗漏前提、失败路径或重要限制。工作流程见 [SKILL.md](../SKILL.md)。

## 信息取舍

- 每段只处理一个问题，每句承担事实、动作、条件、原因或判断标准之一；删掉不承担这些作用的句子。
- 先写定位或结论，再给必要依据与细节。过程文档按执行顺序写，参考文档按查询对象分组。
- 同一事实只详细说明一次，其他位置用短摘要或链接，不重复整段内容。
- 解释会影响读者决策的原因，不解释常识，也不逐句翻译命令。
- 不为凑结构添加概述、背景、意义、优势、总结和展望，没有实际内容就删去章节。
- 不使用“强大、灵活、高效、先进、完善”等无证据评价；性能、可靠性和兼容性结论必须有适用条件与依据。

## 句子与措辞

用具体主语、动词和对象，优先短句、主动语态。技术文档通常直接写“运行”“配置”“检查”，无需“我们首先需要”。中文长句含多个条件或动作时拆分，不用机械字数上限截断技术含义。

以下示例只演示表达方式，具体事实必须先核实：

| 冗余或含糊表达 | 精简表达 |
| --- | --- |
| 为了能够顺利地启动本项目，我们首先需要完成依赖的安装工作。 | 启动前安装依赖。 |
| 需要特别注意的是，修改配置文件之后需要重新启动服务才能使其生效。 | 修改配置后重启服务。 |
| 本模块提供强大且完善的权限管理能力。 | 本模块校验用户角色和资源权限。 |
| 通过引入缓存机制，可以有效提升系统整体性能。 | 缓存查询结果，减少重复读取数据库。 |
| 执行完成后检查系统是否运行正常。 | 请求健康检查接口，确认返回约定状态码。 |

避免“众所周知”“在当今……背景下”“值得注意的是”“综上所述”等套话。保留影响操作结果的条件，不能为缩短文本删掉例外、权限、兼容要求或风险。

## 结构与格式

| 元素 | 规则 |
| --- | --- |
| 标题 | 独立文档一个 H1；主体使用 H2，必要时用 H3，不跳级；局部修订沿用原结构 |
| 段落 | 一段一个主旨，优先一至三句；复杂关系用列表、表格或图 |
| 列表 | 步骤用编号，并列事项用无序列表；避免多层嵌套和只有一个条目的列表 |
| 表格 | 用于字段、配置、职责、状态和方案对比；列名明确，避免长段落挤在单元格中 |
| 代码与标识 | 命令、路径、变量、字段和状态值用行内代码；代码块标明语言 |
| 链接 | 使用有含义的链接文本；仓库内使用相对路径，检查大小写和锚点 |
| 强调 | 仅强调关键约束或操作，不整段加粗，不用表情和装饰性分隔线堆层次 |
| 术语 | 同一概念保持同一名称；仅解释读者需要但未必熟悉的术语，缩写首次出现时按需展开 |

只有篇幅和导航需要时才添加目录。日期、版本和维护者信息仅在有事实依据且对读者有用时保留。

## 命令、配置与示例

- 优先引用项目已有脚本或命令，核实文件、选项、服务名和执行目录。完整示例包含必要上下文，局部片段明确标注位置。
- 只在演示操作、接口或配置时提供示例，不为概念说明硬凑代码。
- 操作后给可观察的成功判据，可以是一句话、状态码、生成文件或必要输出，不要求每段代码都附输出块。
- 区分“预期结果”和“已执行结果”；未运行时不生成看似真实的日志、耗时、成功截图或测试记录。
- 示例值注明替换项和含义，明确替换前不能直接运行；不使用真实凭据、个人路径或生产数据。变量的默认值不能凭经验补全。
- 配置项区分必填、可选与默认值；只注释不明显的逻辑，不把每行代码重复翻译一遍。
- JSON 使用四空格缩进且保持合法；其他代码与配置沿用项目格式。
- 优先用现有自动化、语法和静态检查核对示例。涉及外部状态变更的步骤不自动执行，尤其是部署、重启、迁移、数据删除和权限提升。

## README 头部与徽章

仅在新建 README 或用户明确要求调整头部与徽章时执行。用户或项目指定版式优先；普通润色和局部更新保留原样，其他文档不套用本节。

1. 检查第一个 H1、简介、Logo、顶部导航、已有居中容器和 Shields.io 图片。
2. 没有 Shields.io 徽章时，默认选择二至四枚有依据的技术栈、许可证、CI 或版本徽章；事实不足则减少或省略，不阻塞正文。
3. 将本次适用范围内的 Shields.io URL 统一为 `style=for-the-badge`；用户要求统一整篇时检查全部徽章。保留颜色、Logo、标签、链接目标和其他参数，不改非 Shields 图片。
4. 居中项目主标题、简介和徽章区，复用已有 `<div align="center">`；有 Logo 或顶部导航时保留，不制造嵌套、重复标题或重复徽章。
5. 在第一个 H2 之前结束居中区域，正文保持左对齐，不为装饰重排正文。

Shields.io 参数处理：没有查询参数时添加 `?style=for-the-badge`；已有查询参数时追加 `&style=for-the-badge`；已有 `style` 时仅替换该值。

技术和许可证依据仓库文件；CI 徽章依据真实工作流及正确的仓库、分支；发布版本依据可核实的发布源。不编造“构建通过”、覆盖率或下载量，不把工作流存在写成最近一次构建成功。

## 常见反模式校对清单

- [ ] 一页中反复解释背景、目标和结论，读者仍找不到操作入口。
- [ ] 机械填满模板，出现无关章节、空表格、无依据的通用排障或未替换提示。
- [ ] 只有“优化、完善、保证正常”等抽象措辞，没有对象、条件或可观察结果。
- [ ] 依赖清单被写成已启用功能，设计建议被写成已实现架构，测试通过被写成已上线。
- [ ] 命令缺执行位置、依赖或成功判据，未经运行的结果被写成实测。
- [ ] 声称可回滚却未区分应用与数据，或省略不可逆操作的限制。
- [ ] 文档之间术语、版本、路径或状态冲突，图与正文不一致。
- [ ] 字段、表格和目录树过量，但关键约束、关联或职责缺失。
- [ ] 局部修改扩展到整篇排版，未经请求改动 README 头部或徽章。
- [ ] 适用头部规则时出现样式混用、虚构状态、重复元素或破坏已有导航。
