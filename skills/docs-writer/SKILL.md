# 技术文档写作（docs-writer）

产出事实准确、结构清楚、能指导操作或决策的 Markdown 文档。默认使用简体中文；沿用项目术语、文件名与代码标识。专业性来自准确和可执行，不靠篇幅、术语或装饰。

## 任务边界

- 只创建或修改用户请求的文档，不因为支持六类文档就一次生成全套。
- 局部修改保留原有结构、语言、头部样式与无关内容；明确要求重写时才调整整体结构。
- 路径以用户指定和仓库约定为先。没有约定时，README 放根目录，其他项目文档放 `docs/`，沿用下表文件名。
- 仅要草稿时直接交付 Markdown；在仓库内明确要求编写或更新文档时写入对应文件。
- API 契约规范使用 api-docs；PRD 使用 prd-creator。代码注释、提交信息、PR 描述不套用本流程。
- 编写部署、架构或数据库文档不等于授权部署、改代码或变更数据库；已有操作授权按原范围执行。

## 文档职责与按需读取

先确定读者要完成的事，再读取 [文档结构规范](references/templates.md) 中对应的小节，不加载无关模板。

| 文档 | 回答的问题 | 结构规范 |
| --- | --- | --- |
| `README.md` | 项目做什么，如何开始，去哪里查细节 | [README](references/templates.md#readme) |
| `deployment.md` | 如何部署、验证、更新和恢复 | [部署文档](references/templates.md#部署文档) |
| `architecture.md` | 系统如何组成、协作，边界和取舍是什么 | [架构文档](references/templates.md#架构文档) |
| `tech-stack.md` | 使用哪些技术，版本约束和用途是什么 | [技术栈文档](references/templates.md#技术栈文档) |
| `tasks.md` | 要做什么、先后依赖、如何判定完成 | [开发任务清单](references/templates.md#开发任务清单) |
| `database.md` | 数据如何组织、约束、关联和演进 | [数据库设计文档](references/templates.md#数据库设计文档) |
| 教程、API 使用说明、变更日志 | 完成具体任务、调用能力或了解升级影响 | [其他技术文档](references/templates.md#其他技术文档) |

同一事实只在主文档中完整维护，其他文档保留必要摘要并链接。例如 README 链接部署步骤，架构文档链接技术版本和表结构。只链接已存在或本次确实创建的文档。

## 工作流程

### 1. 确定范围

识别目标文件、读者、使用场景，以及本次是新建、局部修订还是整体重写。先查项目约定和已有文档；仅当缺失信息会实质改变结果且无法从上下文确定时，集中询问。信息充分时直接执行。

### 2. 核实事实

- 按主题检查相关源码、配置、依赖清单与锁文件、部署脚本、数据库模型与迁移、测试及现有文档，不无差别遍历仓库。
- 用当前实现说明行为，用配置说明参数，用锁文件说明解析版本，用实际运行记录说明验证结果；旧文档作为线索，不直接当作事实。
- 区分已实现、拟议方案和未核实信息。用户要求未来设计时明确标为方案，不写成现状；不编造功能、性能、设计理由、负责人或进度。
- 来源冲突时核对适用版本与环境；无法消除的关键冲突简要说明，不静默选择。仓库配置不等于生产环境实际状态。
- 非关键缺口省略；关键缺口集中说明事实缺口和影响，不用占位内容伪装成完整文档。有阻塞时继续完成独立部分。
- 涉及外部产品的当前版本、兼容性或弃用行为时，核验对应版本的官方资料；不为普通措辞修改联网，不把项目版本擅自升级为最新版。

### 3. 组织内容

依据对应文档规范保留完成任务所需的章节。先给定位、结论或适用范围，再给操作、结构或约束；按依赖和执行顺序组织内容。无内容、无依据、不适用的章节直接删去，不填空壳。

### 4. 写作与压缩

- 按 [风格指南](references/style-guide.md) 写短句、具体动作和明确条件。每段提供事实、操作、约束、原因或验收标准，删除不增加信息的句子。
- 步骤用编号列表，并列要点用无序列表，字段与对比用表格；简单结论直接用段落。
- 只在操作需要时提供命令、配置或代码，写清执行目录、前提和成功判据；预期结果不冒充实测输出。
- 图表只用来解释难以用短文说清的关系或流程，组件、名称和方向与正文及证据一致。
- 不重复背景、命令含义和章节结论，不用宣传语、口号、客套话或空泛的“最佳实践”填充正文。

### 5. 核对与交付

按下方清单检查并修正问题。交付时只说明修改文件、关键变化、已验证内容和实质性限制，不复述整篇文档。写入文件后不再在聊天中粘贴全文，除非用户要求。

## README 头部规则

仅在新建 README 或用户明确要求调整头部与徽章时，读取并应用 [README 头部与徽章](references/style-guide.md#readme-头部与徽章)：按事实添加少量徽章、统一 Shields.io 样式并居中头部。用户或项目指定版式优先。一般润色、补充段落和其他文档不触发头部改造。

## 验收清单

- [ ] 文档回答目标读者的问题，章节顺序清晰，没有重复内容、空章节和未替换的模板提示。
- [ ] 功能、命令、配置、版本、路径、任务状态和数据结构均有依据；方案与现状明确区分。
- [ ] 操作包含必要前提和可观察的成功判据；部署、迁移等关键操作说明失败处理或恢复边界。
- [ ] 新增或修改的本地链接、锚点、文件路径与跨文档术语一致；外部链接按本次变更范围核验。
- [ ] 已核对对应文档的专有要求；局部修改未引入无关重排或样式变化。
- [ ] 代表性示例在安全、具备条件且已有授权时验证；否则静态核对并注明未执行，未将检查结果写成生产验收。
- [ ] 无真实密钥、令牌、个人数据和未经脱敏的生产配置。

检查通过即结束。不为验证写作而执行部署、重启服务、迁移、删除数据或权限提升。遇到环境或权限阻塞，停止该项重试，说明未验证部分，继续不受影响的检查。
