# Markdown 文章写作

将用户的主题或素材写成可直接阅读的文章，并实际保存为 UTF-8 Markdown 文件。默认简体中文；语言、受众、篇幅和文风以用户要求为准。

## 写作流程

1. 从请求和已有材料确定主题、读者与文章目的。未指定且上下文无法确定受众时，默认面向了解基本概念、但不熟悉当前主题的读者；专业术语首次出现时简短解释，省去过于基础的铺垫。只有主题缺失或关键歧义会改变内容时才询问；普通风格与篇幅可根据用途合理决定，不固定进行多轮确认。
2. 阅读用户提供的素材或待修改文章。涉及最新数据、产品行为或高风险事实时核验可靠一手来源，正文就近标注来源链接。无法核实的关键事实说明限制，不编造数据、引文、案例或亲身经历。
3. 围绕一个核心问题组织正文，标题准确表达内容，开头直接说明重点。语言精简干练、简明扼要，优先短句和直接表达，删除套话、重复解释与无关铺垫，同时保留必要事实、适用条件、操作步骤和结论。不强制字数，不为简短省略关键解释。章节随内容安排，使用具体说明与有依据的例子，不强制套用前言、三点论或总结。
4. 完成正文后提炼摘要和标签。摘要通常为 80–150 个汉字，短文可更短，只概括文中已有内容；标签通常为 3–5 个不重复的主题词，不加 `#`，用户指定的数量优先。
5. 按下述格式写入文件，回读检查字段、slug 和正文，再交付可打开的文件链接。无法写入时明确说明，仅提供完整 Markdown 内容，不声称已经保存。

## 修改已有文章

- 按请求范围修改，保留无关内容，不将局部修改扩展成整篇重写。
- 修改后检查摘要、标签与章节编号，仅同步受本次修改影响的内容。
- 更改文章总标题时，同步更新 `title`、文件名与 `slug`，根据新标题生成对应的 slug，不沿用旧标题的 slug；先检查目标文件与新 slug 是否冲突，避免覆盖其他文章或复用其他文章的路由。保留原 `created_at`。

## 代码示例

- 区分可独立运行的完整示例与需嵌入现有代码的局部片段。局部片段明确说明插入位置或上下文，以及省略范围，不伪装成完整程序。
- 按需说明运行环境、版本、依赖、输入与预期结果，提供读者复现所必需的信息，不为简单片段重复铺陈环境配置。
- 未实际运行的代码不得声称测试通过；预期结果与实测结果明确区分，已验证时说明相关环境与结果。

## 文件与 slug

- 使用用户指定目录；未指定时保存到当前项目根目录的 `articles/`，没有项目时以当前工作目录为基准。
- 文件名统一为 `标题.md`，不加日期、编号或随机后缀。`title` 元数据与文件名去除 `.md` 后的名称必须一致；文章总标题仅保留在这两处，不在正文重复。
- 拟定标题时避开文件名非法字符。用户指定标题包含 Windows 禁用字符 `< > : " / \ | ? *`、控制字符、尾部空格或句点时，用合适中文标点替换或移除，并同步各处标题，交付时说明调整。保留中文，不自动转为拼音或英文 slug；避开 Windows 保留设备名。
- 使用 `slug` 字段表示 URL 路由标识，不使用 `path` 存储本地文件位置。默认根据文章主题生成简短、有含义的小写英文 kebab-case 标识，如 `reading-notes`；不含域名、首尾斜杠、查询参数、片段或 `.md` 扩展名。网站路由前缀由站点规则决定，例如 `/articles/reading-notes`；用户或项目已有 slug 规范时优先遵循。
- 新建文章或修改 slug 时，在可访问的文章目录或路由配置中检查 slug 是否与其他文章重复；冲突时用更具体的主题词区分，不静默复用。无法检查站点全部路由时，不声称 slug 全站唯一。
- 写入前检查同名文件。明确要求修改该文章时先读取并保留无关内容；新建文章遇到同名文件且未授权覆盖时，询问覆盖还是换标题，不静默覆盖，也不自行添加数字后缀。
- `created_at` 使用实际创建时刻的 ISO 8601 字符串，包含时区偏移。优先使用用户或会话时区，否则使用系统时区；读取当前时间，不将示例时间当作真实时间。修改已有文章时保留原创建时间；原时间缺失且无法查证时询问，不把修改时间冒充创建时间。

## Markdown 格式

YAML frontmatter 放置五项元数据，分隔线之后的 Markdown 为正文，不把长篇正文塞进 YAML。字段名固定为 `title`、`slug`、`tags`、`summary`、`created_at`，分别对应标题、URL 路由标识、标签、摘要、创建时间。正文直接从 `## 1. 章节标题` 开始。

文章正文仅使用二、三、四级 Markdown 标题，编号均以英文句点 `.` 结尾，编号与标题文字间留一个空格：

- 二级：`## 1. 章节标题`、`## 2. 章节标题`。
- 三级：`### 1.1. 小节标题`、`### 1.2. 小节标题`。
- 四级：`#### 1.1.1. 细分标题`、`#### 1.1.2. 细分标题`。

同级编号从 1 连续递增；子级继承父级编号，更换父级后末位从 1 重新计数，例如 `2.1.`、`2.1.1.`。不跳级、不混用无编号标题，不使用一级、五级或六级标题。按内容需要设置层级，不为凑齐三级结构拆碎短文。这些规则约束生成的文章，不改变本技能说明文档的标题结构。

代码块一律使用围栏式 Markdown，并在开始围栏后标注语言，如 `python`、`javascript`、`bash`、`json`。普通文本、日志、伪代码或无法确定语言的内容默认标为 `text`，不得留空或使用无语言标记的缩进代码块。结束围栏不加语言标记；行内代码不受此规则影响。

步骤用有序列表，并列项用无序列表，对比才用表格，加粗只突出关键信息。避免整段加粗、过多小标题或将连续叙述拆成零碎列表。

以下为格式示例，内容和时间仅作演示：

```markdown
---
title: "用阅读笔记留住关键想法"
slug: "reading-notes"
tags:
  - "阅读"
  - "笔记"
  - "知识管理"
summary: "阅读笔记可以从一个值得保留的问题开始。本文介绍记录关键想法、补充个人理解和定期回看的做法，让笔记成为后续思考的材料。"
created_at: "2026-11-16T10:30:00+08:00"
---

## 1. 记录问题

读完文章，先记下值得追问的问题，再用自己的话概括作者的回答。

### 1.1. 补充理解

写清这条观点解决了什么问题，以及它的适用条件。

#### 1.1.1. 区分来源

将作者观点与个人推断分开，方便回查。

## 2. 定期回看

结合新材料修正理解，删去重复记录。
```

字符串正确引用并转义内部引号，避免标题或摘要中的冒号等字符破坏 YAML。多段摘要可用 YAML 块标量；标签始终为列表，时间始终为带引号的字符串。

## 交付检查

- 五项元数据齐全且非空，正文完整，未残留模板说明或待填写内容。
- 文件名与 `title` 一致；改标题时已同步更新对应的 `slug`；`slug` 符合路由约定，不混入本地文件路径，已在可访问范围内检查冲突；正文不重复文章总标题。
- 正文仅用二至四级标题，层级与编号匹配、连续且不跳级，每个编号均以 `.` 结尾。
- 每个代码块的开始围栏均有语言标记；无明确语言时使用 `text`，围栏正确闭合。
- 代码示例的完整性、必要运行条件与输入输出交代清楚，没有将未运行的示例写成已验证结果。
- 表达简明扼要，无套话、重复解释或无关铺垫，必要信息没有因压缩而丢失。
- 术语解释适合目标读者，列表、表格、加粗与标题层级服务于理解，不造成阅读碎片化。
- 摘要与正文一致，标签能表达主题；创建时间真实，修订时没有重置。
- 有可用 YAML 解析器时验证 frontmatter 可解析；没有时检查语法，不为单篇文章强制安装依赖。
- 默认交付文章文件及简短说明，不附加 HTML、封面、发布操作或 Git 提交。
