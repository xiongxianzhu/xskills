## 2. 产品概述

### 2.1. 产品定位

`write-wechat-articles` 是面向中文微信公众号的文章生产 Skill。它将主题、笔记、代码、日志、链接、草稿或图片素材，整理为经过事实核验、适合手机阅读、可复制到微信公众号编辑器的成套文章文件。

当前产品并非单纯的“写作提示词”，而是一条覆盖研究、写作、排版、预览、复制和文件保存的内容生产流水线。

### 2.2. 核心目标

- 帮助用户快速完成短而有用的微信公众号文章。
- 优先保证事实、版本、代码、提示词和引用可靠。
- 根据文章类型选择最小结构，减少空泛铺垫和重复表达。
- 生成适合微信公众号编辑器的富文本内容。
- 同时保留 Markdown 原稿、HTML 源码、预览页和素材说明。

### 2.3. 目标用户

| 用户类型 | 默认基础 | 核心需求 |
| --- | --- | --- |
| 技术作者 | 具备相关技术基础 | 将实践、教程、原理或故障记录整理成公众号文章 |
| AI 创作者 | 已使用过相关 AI 工具 | 分享创作流程、参数、提示词、结果差异和限制 |
| 内容整理者 | 持有笔记、代码、日志、链接或草稿 | 将零散材料压缩成可发布文章 |

### 2.4. 核心使用场景

- 技术教程
- 原理分析
- 故障复盘
- 工具或 AI 产品评测
- AI 漫剧、视频、音乐等创作实践
- 提示词分享
- 现有公众号文章的改写与润色

## 3. 范围边界

### 3.1. 范围内

- 分析用户目标、材料、文章类型和读者收益。
- 必要时检索并核验一手资料。
- 收窄选题并提炼一个核心结论。
- 撰写、改写和润色中文公众号文章。
- 处理技术代码、命令和 AI 提示词。
- 规划真实图片、图片占位和封面提示词。
- 生成 Markdown、公众号 HTML 源码和富文本预览页。
- 提供复制到公众号编辑器的交互能力。
- 自动保存交付文件并避免覆盖已有目录。
- 完成最多两轮质量检查与压缩。

### 3.2. 范围外

- 不自动登录或发布到微信公众号。
- 不自动上传图片到微信公众号素材库。
- 不默认生成图片。
- 不使用 AI 图片伪造技术截图、效果对比或产品结果。
- 不虚构测试、数据、经历、引用和用户反馈。
- 不保证未经实际运行的代码或提示词已通过实测。
- 不在当前工作区不可写时改存到 Skill 安装目录。

## 4. 输入需求

### 4.1. 支持的输入

系统应接受以下一种或多种输入：

- 文章主题或问题
- 原始笔记
- 代码、命令或运行日志
- 网页链接和参考资料
- 已有草稿
- 完整或半成品提示词
- 用户提供的图片或素材说明
- 用户指定的读者、口吻、保存位置或交付范围

### 4.2. 默认假设

- 技术文章默认面向具备基础知识的开发者。
- AI 创作文章默认面向已经使用过相关工具的创作者。
- 默认使用专业、直接、有判断的一线实践者口吻。
- 默认不讲注册流程、基础按钮和行业常识。
- 用户未指定路径时，默认保存到当前工作区。

### 4.3. 澄清规则

- 只有缺失信息会改变技术结论时，系统才应提出问题。
- 每次只提出一个简短问题。
- 不影响技术结论的缺失信息不应阻塞写作。

## 5. 功能需求

### 5.1. 功能列表

| 编号 | 功能模块 | 当前需求 | 优先级 |
| --- | --- | --- | --- |
| F-01 | 意图与材料识别 | 判断目标、材料、文章类型和读者收益 | P0 |
| F-02 | 研究与核验 | 检索一手资料并区分事实状态 | P0 |
| F-03 | 选题收敛 | 提炼一个核心结论并选择最小结构 | P0 |
| F-04 | 文章写作 | 生成短、直接、适合手机阅读的正文 | P0 |
| F-05 | 代码与提示词处理 | 保证完整、自洽、可复制并说明验证状态 | P0 |
| F-06 | 图片与素材规划 | 判断是否需要图片并保持编号一致 | P1 |
| F-07 | 公众号富文本排版 | 生成行内 CSS 的文章 HTML 片段 | P0 |
| F-08 | 富文本预览与复制 | 生成独立预览页并复制正文富文本 | P0 |
| F-09 | 四文件交付 | 保存文章、HTML 源码、预览页和素材说明 | P0 |
| F-10 | 质量检查 | 最多两轮核验、压缩和一致性检查 | P0 |
| F-11 | 失败回退 | 在研究、验证、保存或复制失败时安全降级 | P0 |

### 5.2. F-01 意图与材料识别

系统应：

1. 识别用户是新写、改写、润色还是整理材料。
2. 判断文章属于教程、原理分析、故障复盘、评测、AI 创作实践、提示词分享或混合类型。
3. 明确文章能够给目标读者带来的一个主要收益。
4. 混合类型文章应选择一个主结构，只补充其他类型的必要部分。

**验收标准**：最终文章结构应与主文章类型匹配，不得机械套用统一章节。

### 5.3. F-02 研究与核验

系统应按以下顺序选择来源：

1. 官方文档、模型说明、标准与规范。
2. 官方源码、变更记录与发布说明。
3. 原始论文或作者发布内容。
4. 可靠的二手技术资料和实际案例。

系统应：

- 用户提供链接时先阅读原文。
- 涉及当前版本、价格、政策、功能或平台能力时检索最新资料。
- 将结论标记为“已实际测试”“依据资料整理”“建议尝试”或“作者判断”。
- 资料冲突时优先采用最新一手资料，并指出关键差异。
- 无法检索时只使用用户材料和本地可验证信息，并说明限制。

**验收标准**：参考资料应直接支持正文关键结论；无法确认的内容不得猜测补齐。

### 5.4. F-03 选题收敛与结构选择

系统应将过大的主题收窄到一个能够完整讲清的问题，并从下列结构选择最小闭环：

| 类型 | 必要信息闭环 |
| --- | --- |
| 实战教程 | 目标、前提、最短步骤、完整代码、失败处理 |
| 原理分析 | 核心结论、关键链路、必要例子、适用边界 |
| 故障复盘 | 现象、证据、直接原因、根因、修复、预防 |
| 工具或产品评测 | 测试条件、实际表现、限制、成本、适用范围 |
| AI 创作实践 | 目标、工作流、参数、完整提示词、差异、风险 |
| 提示词分享 | 工具与模型、完整提示词、变量、用法、边界 |

**验收标准**：正文应围绕一个核心问题，不得扩写成术语百科或资料堆砌。

### 5.5. F-04 文章写作

系统应：

- 开头尽快给出问题、结论或实际收益。
- 每段只表达一个重点，优先使用短段落。
- 标题层级一般不超过三级。
- 优先呈现关键代码、完整提示词、实际结果、限制和取舍。
- 删除重复解释、空泛过渡、常识性展开和总结式复述。
- 提供 3 个能够准确兑现正文的标题候选。
- 提供 60 至 100 字的公众号摘要。
- 文末只保留 1 个与正文直接相关的互动问题。
- 不写成产品宣传稿，不使用夸张承诺和悬念欺骗。

**验收标准**：文章应像一线实践者撰写，不得出现虚构经历、营销腔或无依据的精确数字。

### 5.6. F-05 代码与提示词处理

代码和命令应：

- 检查参数、导入、变量和预期输出是否自洽。
- 能运行时执行最小验证。
- 无法运行时只声明静态检查，不宣称已经验证。

提示词应：

- 默认提供一个完整、可直接复制的版本。
- 使用方括号标记可替换变量。
- 标明适用工具、模型、用途和测试状态。
- 只解释显著影响结果的关键变量。
- 不把单次有效结果描述为跨模型稳定能力。

### 5.7. F-06 图片与素材规划

系统应：

- 只在图片能够解释、证明或比较内容时设置正文图片。
- 优先使用用户提供的真实素材。
- 技术截图、效果对比和生成结果必须使用真实素材。
- AI 图片只可用于封面或装饰插图。
- 网络素材应记录来源并提示授权与转载风险。
- 正文不需要图片时，不生成图片占位和正文配图清单。
- 默认提供一条比例为 2.35:1 的封面图提示词。

正文图片占位应采用统一格式，并在所有交付文件中保持编号和位置一致。

### 5.8. F-07 公众号富文本排版

系统应先形成唯一的文章 HTML 片段，再将同一片段用于 `wechat.md` 和 `wechat.html`。

文章 HTML 应：

- 以 `section#wechat-article` 为根节点。
- 使用行内 CSS，不依赖外部样式表、字体、类名、变量或网络资源。
- 使用最大宽度 677px、正文 16px 和约 1.85 行高。
- 使用强调色 `#246ba5` 和统一的 6px 圆角规则。
- 二级、三级标题使用完整层级编号。
- 关键属性显式声明并使用 `!important`，降低公众号编辑器覆盖风险。
- 正确转义代码和提示词中的 `&`、`<`、`>`。
- 保证代码长行可横向滚动。

### 5.9. F-08 富文本预览与复制

`wechat.html` 应基于既有预览模板生成，并满足：

- 单文件打开，不依赖网络资源。
- 完整替换 `{{ARTICLE_HTML}}`。
- “复制到公众号”只复制 `#wechat-article` 正文，不复制工具栏、说明、状态和页面背景。
- 复制内容排除 `<h1>` 标题。
- 优先同时写入 `text/html` 和 `text/plain`。
- Clipboard API 不可用时，回退到选中正文并提示手动复制。

### 5.10. F-09 四文件交付与保存

默认保存结构：

```text
微信公众号文章/
└── YYYY-MM-DD-短标题/
    ├── article.md
    ├── wechat.md
    ├── wechat.html
    └── assets.md
```

| 文件 | 当前职责 |
| --- | --- |
| `article.md` | 3 个标题候选、摘要、Markdown 正文和参考资料 |
| `wechat.md` | 简短说明和一个包含完整文章 HTML 片段的代码块 |
| `wechat.html` | 可独立打开的富文本预览页和复制按钮 |
| `assets.md` | 封面提示词、必要的正文配图清单和素材替换说明 |

保存规则：

- 从最终推荐标题生成不超过 40 个字符的安全目录名。
- 清理 Windows 文件名不安全字符。
- 同名目录存在时追加 `-2`、`-3` 等后缀，不得覆盖。
- 用户指定路径、文件名或交付范围时，以用户要求为准。
- 保存成功后，对话只返回摘要、四个文件链接和校验结果，不重复全文。

### 5.11. F-10 质量检查

系统应在初稿后检查一次，压缩后再检查一次，最多两轮。检查范围包括：

- 技术事实与来源
- 内容效率与文章类型闭环
- 公众号排版和四文件一致性
- 视觉规则和深色主题兼容
- 图片真实性与授权风险
- 文件保存和冲突处理
- 文风、AI 腔、营销表达和版权风险

两轮后仍无法确认关键事实时，系统应列出缺口并停止扩写。

### 5.12. F-11 失败回退

| 失败场景 | 当前要求 |
| --- | --- |
| 来源冲突 | 采用最新一手资料并说明差异 |
| 无法检索 | 使用用户材料和本地事实，说明研究限制 |
| 无法运行示例 | 只报告静态检查结果 |
| 无法确认授权 | 只给素材建议并提示风险 |
| 当前工作区不可写 | 在对话中输出完整交付，不写入 Skill 目录 |
| 富文本复制失败 | 保留选中状态，提示用户手动复制 |

## 6. 非功能需求

### 6.1. 准确性

- 不得虚构事实、版本、参数、数据、结果、经历、引用或反馈。
- 关键结论必须具有可追溯来源或明确的事实状态。

### 6.2. 可读性

- 文章应适合手机阅读，短段落、少层级、低信息噪声。
- 不得通过装饰符号、密集加粗或空泛金句制造节奏。

### 6.3. 一致性

- Markdown 正文、HTML 片段、预览页和素材清单的内容及图片编号应一致。
- `wechat.md` 与 `wechat.html` 必须使用同一个文章 HTML 片段。

### 6.4. 兼容性

- HTML 应适应微信公众号编辑器对样式的覆盖。
- 预览页应在无网络环境下独立打开。
- 复制失败时应提供不丢失内容的回退路径。

### 6.5. 文件安全

- 不得覆盖已有文章目录。
- 不得把生成内容写入 Skill 安装目录作为保存回退。
- 文件和目录名应兼容 Windows 文件系统。

### 6.6. 成本边界

- 每篇文章最多执行两轮完整修订。
- 资料不足时应缩小结论或停止，不得无限扩写。

## 7. 内容与文件关系

```text
用户输入
  → 研究资料与事实状态
  → 核心结论与文章结构
  → 文章正文内容
      ├─ Markdown 表达 → article.md
      └─ 唯一文章 HTML 片段
      ├─ wechat.md
      └─ 预览页模板 + 文章片段 → wechat.html
  → 图片与封面信息 → assets.md
```

当前规范要求 Markdown 与 HTML 内容一致，但没有定义可执行的中间数据模型或确定性转换器。

## 8. 依赖与约束

### 8.1. 外部依赖

- 可访问官方文档、源码、论文和发布说明的检索能力。
- 可写入当前工作区的文件系统。
- 支持 Clipboard API 的浏览器，或允许用户手动复制。
- 微信公众号编辑器对粘贴富文本和行内 CSS 的实际支持。

### 8.2. 内部依赖

- 六类文章的最小结构规则。
- 研究与事实核验规则。
- 微信公众号排版规范。
- 发布前质量清单。
- 固定的 HTML 预览页模板。

## 9. 现状验收场景

### 9.1. 仅提供主题

给定一个涉及当前产品版本的技术主题，系统应检索官方资料、收窄问题、完成文章并保存四个文件。

### 9.2. 提供草稿和代码

给定已有草稿与代码，系统应保留有效事实和核心观点，删除重复内容，核对代码并生成公众号交付物。

### 9.3. 提示词分享

给定一个 AI 创作提示词，系统应输出完整提示词、可替换变量、适用模型、测试状态和能力边界。

### 9.4. 无法联网

无法检索时，系统应明确说明限制，只基于用户材料和本地可验证信息写作，不得伪造来源。

### 9.5. 保存目录冲突

目标目录已存在时，系统应创建带数字后缀的新目录，不得覆盖已有文章。

### 9.6. 浏览器复制受限

Clipboard API 不可用时，预览页应选中不含 H1 的文章正文，并提示用户手动复制。

## 10. 当前问题与风险

本节是对现状的分析，不属于现有需求。

| 编号 | 问题 | 影响 | 严重度 |
| --- | --- | --- | --- |
| I-01 | 产品边界过宽，同时承担研究、写作、排版、文件生成和浏览器复制 | 单个 Skill 复杂度高，任何环节变化都会影响整体稳定性 | 高 |
| I-02 | “短而有用”没有字数、阅读时长或信息密度标准 | 不同执行结果可能长度差异很大，难以验收 | 高 |
| I-03 | 缺少账号定位、品牌语气、读者阶段和内容目标等关键输入 | 默认口吻容易同质化，难以适配不同公众号 | 高 |
| I-04 | 默认主动研究没有按任务类型区分 | 单纯润色用户定稿时也可能产生不必要的检索和改写 | 中 |
| I-05 | Markdown、HTML 与四文件的一致性只靠提示词约束 | 缺少确定性转换，容易出现正文、图片编号或样式漂移 | 高 |
| I-06 | `wechat.md` 与 `wechat.html` 都保存完整 HTML | 交付重复，用户需要理解两个相似文件的不同用途 | 中 |
| I-07 | 默认总是生成四个文件和封面提示词 | 对只想要正文或只想润色的用户过重 | 中 |
| I-08 | 固定强调色、圆角、字号和组件样式 | 无法适配不同公众号的品牌视觉体系 | 中 |
| I-09 | 样式规范存在边界冲突 | “不使用阴影和装饰圆点”与代码块阴影、红黄绿圆点同时存在 | 中 |
| I-10 | 深色主题规则存在表述冲突 | 一处要求正文颜色交由微信主题处理，另一处又规定正文使用固定颜色 | 高 |
| I-11 | 文章标题在交付链路中的唯一性不清楚 | 同时存在 3 个候选标题、最终推荐标题、HTML H1 和复制时移除 H1 的行为 | 高 |
| I-12 | 质量清单很长但缺少分级 | 所有文章都执行大量检查，关键阻断项和一般优化项没有区分 | 中 |
| I-13 | 缺少文章效果目标 | 没有打开率、读完率、收藏价值、转化动作或搜索价值等内容目标 | 高 |
| I-14 | 缺少引用与正文观点的映射结构 | 虽然要求一手来源，但难以快速审计某条结论由哪个来源支持 | 中 |
| I-15 | 没有 HTML 结构校验和视觉回归机制 | 行内 CSS、标签闭合、复制范围及微信粘贴效果主要依靠人工检查 | 高 |
| I-16 | 固定最多两轮修订，但没有定义每轮的退出条件 | 可能做无效重写，也可能在关键错误未解决时停止 | 中 |
| I-17 | 文章类型覆盖很广，缺少领域边界 | 技术文章与 AI 创作文章的证据、风格和结果验证方式差异较大 | 中 |
| I-18 | 默认写入当前工作区 | 可能在非内容项目中产生较大的文章交付目录 | 低 |

## 11. 重新设计前的决策清单

以下问题应由新版产品设计明确回答，不应直接沿用当前实现。

### 11.1. P0 决策

| 编号 | 必须决定的问题 | 主要选项 |
| --- | --- | --- |
| D-01 | 新 Skill 的核心产品边界是什么 | 只负责写作；写作与研究；完整公众号交付流水线 |
| D-02 | 谁是第一目标用户 | 技术作者；AI 创作者；泛知识博主；支持可配置角色 |
| D-03 | 一篇文章的首要成功指标是什么 | 信息准确；读完率；收藏价值；转化；个人品牌表达 |
| D-04 | 哪些信息必须在写作前确认 | 账号定位、读者、文章目标、篇幅、口吻、素材可信度 |
| D-05 | 研究何时触发 | 所有新写任务；仅事实变化主题；用户选择；缺失证据时触发 |
| D-06 | 内容的唯一真相源是什么 | Markdown；结构化文章模型；HTML |
| D-07 | 默认交付应该有几个文件 | 单一正文；正文加发布稿；按用户选择生成完整包 |
| D-08 | 排版属于 Skill 核心还是独立阶段 | 写作内置；独立渲染器；独立 Skill |
| D-09 | 如何定义可验收的文章质量 | 字数与结构规则；事实评分；内容目标评分；人工审核门槛 |
| D-10 | 如何保证跨文件一致性 | 纯提示约束；确定性脚本；结构化中间数据加渲染器 |

### 11.2. P1 决策

| 编号 | 需要决定的问题 | 主要选项 |
| --- | --- | --- |
| D-11 | 视觉风格是否可配置 | 固定主题；多个预设；账号级设计令牌 |
| D-12 | 图片能力包含到什么程度 | 只给建议；生成提示词；调用生图；管理素材 |
| D-13 | 标题与摘要如何选择 | 只生成候选；给出推荐及理由；按内容目标评分 |

## 12. 重建设计的输入基线

后续使用 ChatGPT 重新设计时，至少应提供：

1. 本 PRD 的第 2 至第 9 节，作为旧版能力基线。
2. 第 10 节问题清单，要求逐项判断保留、修复或删除。
3. 第 11 节决策清单，先完成产品选择，再设计 Skill 文件结构。
4. 3 至 5 篇理想公众号文章样本，用于定义账号风格和质量标准。
5. 3 个真实任务样例，分别覆盖新写、材料整理和改写。

新版设计不应默认复刻当前四文件交付、固定视觉主题或全流程耦合，除非这些选择经过重新确认。
